# 施工方学习记录与交付协议 v1.0

更新：2026-11-28 · 类型：**增量补录协议**，适用 **Antigravity** 与 **Cursor**（各自一份学习记录，规则相同），与各自的《施工协议》并读；冲突以本协议为准。

## 1. 目的

1. 让每一次新尝试的**失败点**与**通过点**都留下来，下次施工前先过一遍，**不重复踩坑**。
2. 把已验证可用的写法/语言收成**基本盘**——新路线跑不通时的最后保底（fallback）。
3. 每次交付都能一眼看出**改了什么**（新增/删除/修改，未改变的不列）。
4. 被退回的重交付，**先确认链路被准确调用**再交，避免"文件交了但没被用上"。

## 2. 学习记录（学习记录 = 知识库，不瘦身）

**位置**：仓库 `learning/antigravity/LEARNING_LOG.md`、`learning/cursor/LEARNING_LOG.md`；Drive `antigravity/learning/`、`cursor/learning/`（镜像，内容一致）。
**四段结构**：
| 段 | 内容 |
|---|---|
| 基本盘 BASELINE | 已验证可用的写法/语言（带验证证据）；新路线跑不通时回到这里 |
| 施工前已读 REVIEWS | 每次施工前过记录的登记（分支、标签、看到几条失败） |
| 尝试 TRIES | 每次尝试：结果（PASS/FAIL/PARTIAL）、标签、目标、**失败点/通过点**、与已失败路线的不同 |
| 成功记录 SUCCESS | 通过的尝试附"下轮/其他方向可走" |

**规则**
1. **每次施工前必须过一遍**：`python3 scripts/learning_log.py review <ag|cu> <分支> <标签>`，列出基本盘、相关失败、成功方向，并登记"已读"。CI 强制。
2. **每次新尝试都要记**，通过的和失败的都记：`learning_log.py add …`。失败要写清**现象、原因（或"未查明"）、证据**；通过要写清**哪里通过**并填 `--next`（下轮/其他方向可走）。CI 要求每个交付分支至少有一条本分支的尝试记录。
3. **鼓励多维度开发**：可以从多个维度同时试；每个维度都要留记录。
4. **不重复踩坑**：新尝试的标签若包含某条已失败的标签组合，工具会拦下，必须写 `--differs`（这次哪里不同）；写不出不同就换方向。
5. 标签用英文小写、逗号分隔（例：`shopline-syntax,hotspot,glb`）；行内不写 `|`。
6. 两份记录互相可读，但**各写各的**。

**基本盘与 fallback**
- **基本盘收录的是"已有可用的写法/语言"**（如 Shopline 模板语法、已验证的组件写法、Worker 的既有写法）——这是我对"已有可用的语言"的理解，**请你确认**。
- 收录条件：至少一次 PASS 且有证据；用 `learning_log.py base <角色> <标签> <写法> <证据>`。种子条目来自官方源码、既有 Worker/接口、SpaceVanta-Base 的已测行为；Cursor 的种子条目只有名称，**首次接手须核实并补写**。
- **fallback 规则**：新路线的闸门不过、且没有已知修复（或自动跑额度用尽）时，**回到基本盘路线交付**，并在 TRIES 里记下新路线为何没走通。**不得静默用新写法改写基本盘**。

## 3. 交付清单（每次交付一份）

- 位置：仓库 `delivery/<分支名，/ 换成 ->>/MANIFEST.md`；Drive `<类别>/<事项>/<角色>/delivery/<分支>/`。
- 内容：**新增 / 删除 / 修改**三类文件；**未改变的不列**。重命名记为修改（`旧 -> 新`）。基础设施路径（`delivery/`、`learning/`、`code-checklist/`）不列入。
- 生成：`python3 scripts/delivery_manifest.py make <base> <分支>`；CI 用实际 diff 对账，**漏列或多列都判失败**。
- Drive 只留每个事项最近 3 份交付清单（与清单瘦身口径一致，**待确认**）；完整历史以 git 为准。

## 4. 被退回的重交付

1. 读退回原因，先过学习记录（`review`），失败点写进 TRIES。
2. 修改后跑**链路验证**：`python3 scripts/chain_check.py run <base> <分支>`——"被准确调用"的含义：
   - **Antigravity（网页）**：引用的组件、区块、分组存在；`asset_url` 指向的资源存在；`| t()` 的键在 `i18n/en.json` 存在；模板 JSON 里的区块类型存在；区块带 `presets`。只检查**本次改动的文件**，不翻旧账。
   - **Cursor（Worker）**：`wrangler.toml` 的入口存在、对应契约文件存在；脚本只做静态底线，**契约测试结果仍须施工方自行提交**。
   - 另：L5 里点名的每个热点/资产/接口是否都被实际引用，由施工方在 VERIFY 里逐项说明（脚本查不到的部分）。
3. 通过后用 `delivery_manifest.py make … --redelivery "<退回原因>"` 生成交付清单；CI 会复跑链路验证，没有 `RESULT: PASS` 的 `CHAIN_CHECK.md` 不放行。

## 5. 三份记录的分工（别混）

| 记录 | 管什么 | 谁写 |
|---|---|---|
| 代码清单 code-checklist | 全局/驱动层与模板内部代码的对账、锁、源实现（仅 Antigravity） | 脚本 |
| 学习记录 | 尝试的失败/通过、基本盘、成功方向 | 施工方 |
| 交付清单 | 这一次交付的新增/删除/修改 | 脚本 |

## 6. 分支与权限

- 正式施工分支 `ag/*`、`cu/*`：可写自己的学习记录与 `delivery/`。
- 自动跑沙箱分支 `ag-u/*`、`cu-u/*`（见《模型自动化迭代协议》）：只能写 `u-runs/<角色>/` 与自己的学习记录。

## 7. 待你确认
1. "已有可用的语言"理解为"已验证可用的写法/语言规则"（基本盘）。
2. Drive 交付清单只留最近 3 份。
3. fallback 触发条件按"闸门不过且无已知修复/额度用尽"，没设固定次数。
